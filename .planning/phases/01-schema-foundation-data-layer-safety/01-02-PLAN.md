<objective>
Build the bundled canonical schema (SCHEMA-01, success criterion #2) by reconciling the four authoritative gsd-core sources, and prove completeness with an automated flatten-and-diff test.

This implements the locked decisions: D-01 (ship full structural schema now — keys, types, enums, defaults, category groupings — plus a one-line description per key; design the `x-*` slot to hold per-option prose later without a structural change), D-02 (reconcile MULTIPLE sources, not one), and D-03 (manifest `validKeys` is the primary authority for "which keys exist"; `dynamicKeyPatterns` is the source of truth for pool/agent-map key shapes). Per RESEARCH.md § Critical Finding, `validKeys` alone undercounts real keys by ~30 leaf paths per fixture, so the reconciliation MUST also union the `capability-registry.cjs` `configSchema` (third source, resolves the missing `workflow.*` toggles and ships real prose) and `config-defaults.manifest.json` `CONFIG_DEFAULTS` (defaults).

Per the USER DECISION and RESEARCH.md § Critical Finding: `gates.*` (8 boolean leaves) and `safety.*` (2 boolean leaves) are present, consistent across all three real fixtures, and actively consumed at runtime, but declared in none of the three schema sources — so they MUST be INCLUDED in the bundled schema, modeled from the observed real-fixture shape (all boolean leaves) and tagged `"x-provenance": "fixture-observed"` (distinct from the `manifest`/`capability-registry`/`config-defaults` labels used for authoritative keys). This makes a real `config.json` contain zero keys missing from the schema. A Phase 6 live-reconcile (SCHEMA-05) re-verifies the fixture-observed shape against upstream gsd-core. (This REVERSES the earlier "let gates/safety fall to the unknown bucket" guidance.)

Purpose: A single JSON Schema 2020-12 + `x-*` artifact that drives both Ajv validation (Plan 03) and the effective-value merge (Plan 05), forward-compatible with the Phase 6 live reconcile.
Output: `bundled-schema.json`, its reconciliation script, a curated-docs overlay, and a completeness test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gsd-core source files → build script | The build script reads gsd-core files as data; it must never `require()`/`eval()` them as executable code (supply-chain / RCE avoidance, ARCHITECTURE Anti-Pattern 2) |
| bundled-schema.json patternProperties → Ajv (Plan 03) | Regexes compiled by Ajv at validation time; a catastrophic-backtracking pattern would be a DoS vector |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-ReDoS | Denial of Service | `patternProperties` regexes in bundled-schema.json | medium | mitigate | Source every dynamic-key regex directly from the manifest's own `dynamicKeyPatterns[].source` (simple bracket char-classes like `^model_overrides\.[a-zA-Z0-9_-]+$` — no nested quantifiers, no catastrophic backtracking). Do NOT author new complex patterns (RESEARCH § Security Domain). |
| T-01-RCE | Elevation of Privilege | build-schema.ts reading capability-registry.cjs / config-schema.cjs | high | mitigate | Read the `.cjs` sources as data (parse the exported object literal / require the JSON manifests) — the two `.manifest.json` sources are pure JSON. For the `.cjs` `configSchema`, extract via a scoped `require()` of the local installed module is acceptable ONLY for the locally-installed trusted gsd-core (not remote content); live-repo fetch + AST-parse is a Phase 6 concern. Never fetch+execute remote source in Phase 1. |
| T-01-Drift | Tampering | Fixture-observed `gates.*`/`safety.*` schema entries | low | mitigate | Model gates.*/safety.* from the consistent 3-fixture observed shape (all boolean leaves) and tag each `"x-provenance": "fixture-observed"` so the entries are auditable and a Phase 6 live-reconcile (SCHEMA-05) can specifically re-verify them against upstream gsd-core. Including them (per USER DECISION) makes a real config.json contain zero keys missing from the schema. |
</threat_model>
