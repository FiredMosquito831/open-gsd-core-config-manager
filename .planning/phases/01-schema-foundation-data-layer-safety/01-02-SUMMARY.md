## Decisions Made
- **Dynamic-map container path derivation uses the manifest's own regex, not prose parsing.** The `description` field for entries like `model_profile_overrides.<runtime>.<opus|sonnet|haiku>` and `dynamic_routing.<enabled|escalate_on_failure|max_escalations|tier_models.<light|standard|heavy>>` contains nested `<...>` placeholders that don't strip cleanly with a simple "trim trailing `.<...>`" approach. The `source` regex is authoritative and unambiguous (literal segments up to the first regex metacharacter), so `deriveContainerPath()` parses that instead.
- **x-category is structural (build script), x-description prose is curated (overlay).** D-01 frames "category groupings" as part of the full structural schema, distinct from per-key prose. `build-schema.ts`'s `deriveCategory()` heuristic assigns a category to every entry (including capability-registry-sourced ones) mechanically from key-namespace prefix; `curated-docs.json` only overrides categories the heuristic gets wrong (14 keys, e.g. `commit_docs`/`search_gitignored`/`granularity` → Planning, `brave_search`/`exa_search`/`firecrawl` → Discovery).
- **x-options enum stubs are auto-generated, not hand-authored.** Rather than requiring curated-docs.json to redundantly enumerate every enum's option keys, the build script post-processes every entry with an `enum` array and fills any missing option key with `{"x-description": ""}` — mechanical, DRY, and satisfies D-01's "design the slot now" requirement without curated-docs.json needing enum-value knowledge.

**1. [Rule 2 - Missing Critical Functionality] Added parallelization.* sub-keys as a second fixture-observed group**
- **Found during:** Task 3 (authoring the completeness test's Part B fixture-flatten diagnostic)
- **Issue:** All three real fixtures expand `parallelization` into a 6-key nested object (`enabled`, `plan_level`, `task_level`, `skip_checkpoints`, `max_concurrent_agents`, `min_plans_for_parallel`). None of the four reconciled sources (manifest validKeys, dynamicKeyPatterns, capability-registry configSchema, config-defaults CONFIG_DEFAULTS) declare this expanded shape — only the bare `parallelization: boolean|object` polymorphism is documented in gsd-core's own reference docs. Grepping the entire gsd-core installation for these six sub-key names returned zero hits — this is a genuinely undocumented, real-fixture-only shape, structurally identical to the `gates.*`/`safety.*` finding RESEARCH.md already flagged, but not itself called out by RESEARCH (a gap in the prior research session, not a planning oversight). Leaving it unmodeled would have violated SCHEMA-01's own success criterion ("zero keys in a real config.json are absent from the bundled schema") for this project's own fixture.
- **Fix:** Added a `FIXTURE_OBSERVED_TYPED_KEYS` group in `build-schema.ts` (same `x-provenance: fixture-observed` treatment as gates/safety, but with per-key types since these mix booleans and numbers rather than being uniformly boolean), widened the bare `parallelization` entry's `type` to `["boolean", "object"]` to match its documented polymorphism (`planning-config.md` § Field Interactions #4), and authored one-line descriptions for all 6 new keys in `curated-docs.json`.
