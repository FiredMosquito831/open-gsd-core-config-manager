<objective>
Build the corruption-proof write pipeline (SAVE-02, success criterion #4) with the validation-blocking gate (SAVE-01, success criterion #3), and prove atomicity under repeated mid-save process kills.

The outer Windows retry wrapper is NOT optional hardening — RESEARCH.md § Verified: write-file-atomic Has No Built-In Windows Retry confirms (via still-open GitHub issue #227 on the pinned 7.0.1) that `write-file-atomic` does NOT retry `EPERM`/`EBUSY`/`EACCES` on the rename when Windows Defender / the indexer / a concurrent process transiently locks the target. The wrapper fills a real, currently-unpatched gap in the pinned dependency. The pipeline order (RESEARCH § Decision: Atomic-Write Mechanics): `proper-lockfile.lock` → `validate()` (BLOCKS before any write on failure) → `writeFileAtomic(..., { fsync: true })` inside the retry loop → `release()` in `finally`. write-file-atomic's default same-directory temp placement must NOT be overridden (cross-device temp → non-atomic copy+delete / EXDEV).

Purpose: The atomic, validated, lock-guarded save that Phase 2's server and Phase 5's revert-as-write reuse without a special-case path.
Output: `atomic-write.ts`, its fault-injection unit test, and the standalone kill-mid-save stress harness.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Process interruption (kill/crash/power loss) during write → config.json on disk | A non-atomic write can leave a truncated file that breaks every subsequent gsd-core command |
| Concurrent writers (two tabs / gsd CLI + this tool) → same config.json | Racing writes can interleave and corrupt |
| Invalid in-memory object → disk | A structurally-invalid config must never be partially written |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-AtomicWrite | Tampering / Denial of Service | saveConfig write path | critical | mitigate | `write-file-atomic@7` (temp-in-same-dir → fsync → rename) + outer `EPERM`/`EBUSY`/`EACCES` retry-with-backoff filling the library's known unpatched Windows gap (issue #227). Proven by the kill-mid-save harness (success criterion #4) and fault-injection unit tests. This IS SAVE-02. |
| T-01-Concurrent | Tampering | concurrent writers | high | mitigate | `proper-lockfile` advisory lock held across the write, released in `finally`. Locking + atomic write together (RESEARCH: they solve different halves). |
| T-01-PartialWrite | Tampering | validation gate | high | mitigate | `validate()` runs before any write; on failure saveConfig throws before `writeFileAtomic` is reached — no partial write (SAVE-01). Unit test asserts writeFileAtomic is not called on invalid input. |
