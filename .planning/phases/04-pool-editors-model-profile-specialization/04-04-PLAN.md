## Scope Rationale

This plan deliberately retains its broad but coherent scope because the Profiles chapter, copy-first focused editor, post-save runtime notice, shared editor/store/navigation styling integration, and end-to-end tests must change together to preserve the frozen save boundary. Splitting would cause overlapping ownership of `ConfigEditor`, `uiStore`, and `styles.css` and weaken the single-flow PROF-01–04 verification.

## Trust Boundaries
| Boundary | Description |
|---|---|
| profile/catalog data → browser editor | Catalog-derived profile choices can otherwise be mistaken for arbitrary user identity data. |
| changed draft paths → post-save notice | Notice derivation must not expose changed values or make unverified runtime claims. |
| ConfigEditor candidate → existing local API | Profile/pool edits must retain token, origin, opaque-id, validation, atomicity, and snapshot safeguards. |

## ASVS Level 3 Threat/Control Coverage
| Control ID | ASVS Area | Trust Boundary | Enforcement and Executable Evidence |
|---|---|---|---|
| ASVS-04-04-V5 | V5 Input Validation | profile/catalog data → editor | Copy-first project-configuration creation, descriptor-constrained assignments, and profile card/editor/create test contracts prevent arbitrary profile objects; the optional session label is local-only and is never serialized, reloaded, or validated as durable identity. |
| ASVS-04-04-V4 | V4 Access Control | profile draft → safe save | `ConfigEditor` remains the sole mutation owner and sends the full project candidate only to the existing opaque-id/token/origin-protected route; no profile endpoint exists. |
