A malformed/unparseable `index.json` must throw rather than silently reset history — losing history silently is the failure mode this whole feature exists to prevent.

    `recordSnapshot(configPath: string, priorContent: string | null, root?: string): Promise<string | undefined>` — returns `undefined` immediately when `priorContent` is `null` (D-11: nothing existed to snapshot; no directory, no phantom index entry).     Create `packages/server/src/snapshot-store/save-with-snapshot.ts` exporting `SaveResult` and `saveWithSnapshot`.

    `SaveResult` is the discriminated union `{ ok: true; snapshotId?: string; warning?: string } | { ok: false; errors: object[] }`. This shape is load-bearing: Plan 05's `PUT /api/configs/:id` route returns it directly as the API envelope, and Phase 5's revert reuses it. Treat it as a frozen contract.

    `saveWithSnapshot(configPath: string, nextConfig: object, validate: (data: unknown) => ValidationResult, deps?: SaveDeps): Promise<SaveResult>` where `SaveDeps` is `{ record?: typeof recordSnapshot; root?: string; warn?: (message: string) => void }`. Every dependency is injectable — that is what makes the D-12 "failing recorder" test possible without module mocking, and it matches `saveConfig`'s own dependency-injected `validate` parameter.

    Orchestration, in exactly this order (D-11):
    1. Read the current on-disk content as a UTF-8 string. `ENOENT` means the file does not exist yet — set prior content to `null` and continue (first-ever save; nothing to snapshot). Any other error code rethrows.
    2. Call Phase 1's `saveConfig(configPath, nextConfig, validate)` **unmodified**. Catch `ValidationError` and return `{ ok: false, errors: err.errors }`. Any other error rethrows (a genuine write failure is not a soft failure — the user must know their save did not happen).
    3. Only after the save succeeds, attempt the snapshot: call `record(configPath, priorContent, root)` inside its own narrowly-scoped try/catch. On success, return `{ ok: true, snapshotId }`.
    4. On snapshot failure (D-12), do NOT rethrow and do NOT fail the save. Build the warning message using the exact 02-UI-SPEC.md copy: the sentence beginning "Saved successfully, but history was not recorded" followed by a parenthesised short reason (the error's `code` or `message` — never the config content, never a stack trace). Pass it to `warn` (default `console.warn`) and return `{ ok: true, warning }` with `snapshotId` left `undefined`.

    Structure this as three separate concerns with their own try blocks — not one blanket try/catch — mirroring how `atomic-write.ts` isolates its lock-release `finally` from the validate/write logic above it. The asymmetry is deliberate and must be visible in the code: a `saveConfig` failure propagates; a `recordSnapshot` failure is swallowed into a warning.

    Do not import `env-paths` here; the store owns that.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server process → user's project filesystem | The config write target. Crossing it wrongly corrupts or destroys user data. |
| Server process → OS per-user app-data directory | The snapshot store. A full plaintext copy of the user's config crosses this boundary on every save. |
| Untrusted config content → log/error output | Config values may be secret-shaped (API keys); they must never surface in a warning, error, or log line. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06 | Information Disclosure | `snapshot-store/paths.ts` — snapshot files written inside the tracked project (or its `.git`), leaking config history into the user's repo/commits | medium | mitigate | `snapshotDirFor` resolves exclusively under `env-paths('gsd-config-manager').data` (D-07); the path is never derived from the config's own directory. Verified by the test "snapshot is stored outside the tracked project directory", which asserts the snapshot dir is not a descendant of the config dir and contains no `.git` segment. |
| T-02-12 | Information Disclosure | `save-with-snapshot.ts` — the D-12 warning or a thrown error echoing config content (API keys, tokens) into stdout/logs | medium | mitigate | The warning message is built from the error's `code`/`message` only, never from `priorContent` or `nextConfig`; no stack trace is printed. Mirrors Phase 1's `ValidationError`, which carries only Ajv field errors. Verified by the test "save succeeds even if snapshot recording fails", which asserts the warning contains no substring of the config content. |
| T-02-13 | Tampering / Denial of Service | `readIndex` — a corrupt or truncated `index.json` silently resetting history to empty, causing the next save to overwrite snapshot `1.json` | medium | mitigate | `readIndex` returns an empty index only on ENOENT; a malformed `index.json` throws rather than resetting. | T-02-15 | Elevation of Privilege | Prototype pollution via `JSON.parse` of an attacker-influenced `index.json` (`__proto__` key) | low | mitigate | The index is read only for its `entries` array and its numeric `seq`; no key from the parsed index is ever used as an assignment target or spread onto an object literal.
