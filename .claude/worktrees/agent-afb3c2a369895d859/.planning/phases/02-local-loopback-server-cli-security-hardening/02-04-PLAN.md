<objective>
Build the Fastify application: root-scope Host allowlist, `/api`-scoped Origin guard + CORS lock + per-launch token guard, unguarded static serving of `dist/client`, and a token-guarded `GET /api/health` route.

Purpose: Success criterion 2 — "A request with a non-allowlisted Host header, or a cross-origin request from an unrelated site, is rejected by the server; a mutating request missing the per-launch token is rejected." This is the MCP-Inspector-CVE-2025-49596 (CVSS 9.4) threat class: a local HTTP server with filesystem write access, reachable by every other browser tab on the machine. Three independent layers are required because each covers the others' gap — a browser cannot forge `Host` (defeats DNS rebinding), CORS is browser-enforced only (useless against `curl`), and the token covers non-browser callers.

<cors_correction>
**Read this before implementing the Origin check — it corrects 02-RESEARCH.md.**

02-RESEARCH.md Pattern 3 implies `@fastify/cors` with a function-based `origin` callback satisfies the cross-origin requirement. It does not, on its own. When the callback answers `false`, `@fastify/cors` simply **omits the `Access-Control-Allow-Origin` header** — the request still reaches the handler and still returns 200; it is the *browser* that then withholds the response from the calling page. Success criterion 2 says the request must be "**rejected by the server**", and `fastify.inject()` (the test vehicle 02-VALIDATION.md mandates) has no browser to enforce anything.

Therefore this plan implements **both**:
- `@fastify/cors` with an exact-string origin check — for correct preflight `OPTIONS` handling, `Vary`, and allowed-headers negotiation.
- A separate `origin-guard` `onRequest` hook in the `/api` scope that returns **403** when an `Origin` header is present and does not exactly equal the computed loopback origin. Absent `Origin` (same-origin navigations, `curl`) is not rejected here — the token guard is what covers that caller class (D-04).

This is a deliberate deviation from the research sketch, required by the success criterion and by testability.
</cors_correction>

    Create `packages/server/src/plugins/host-guard.ts` exporting `registerHostGuard(app, ctx)`. It adds an `onRequest` hook that reads `req.headers.host`, and when it is absent or not present in `ctx.allowedHosts`, replies 403 with the body `{ ok: false, errors: [{ message: 'Host not allowed' }] }` — a fixed, static message that never echoes the received Host value back (an Information Disclosure guard mirroring `ValidationError`, which never carries the config body). This hook is registered at the **root** scope by `app.ts`, so it fires for static assets too: a rebound origin must not be able to scrape the SPA shell either. A browser cannot forge `Host`, which is why this single check defeats the entire DNS-rebinding class regardless of what the attacker's domain resolves to.

    Create `packages/server/src/plugins/origin-guard.ts` exporting `registerOriginGuard(app, ctx)`. It adds an `onRequest` hook that replies 403 with `{ ok: false, errors: [{ message: 'Origin not allowed' }] }` when an `Origin` header is present AND does not exactly equal `ctx.corsOrigin` (or when `ctx.corsOrigin` is null — an unsealed context must fail closed, not open). A request with no `Origin` header is passed through: same-origin navigations and non-browser callers legitimately omit it, and the token guard is what covers those. Read `<cors_correction>` above — this hook, not `@fastify/cors`, is what makes the server actually *reject* a cross-origin request. This hook is registered in the `/api` scope.

    Create `packages/server/src/plugins/token-guard.ts` exporting `registerTokenGuard(app, ctx)`. It adds an `onRequest` hook that lets `OPTIONS` requests through untouched (CORS preflights carry no custom headers by definition; guarding them would break every legitimate preflight) and otherwise compares `req.headers['x-gsd-token']` against `ctx.token`. Compare in constant time with `crypto.timingSafeEqual` over UTF-8 buffers, after a length check (`timingSafeEqual` throws on unequal lengths, so a length mismatch is an immediate reject). On mismatch or absence, reply 403 with `{ ok: false, errors: [{ message: 'Missing or invalid launch token' }] }` — never echoing the supplied token. Guard reads as well as writes (D-04): an unauthenticated `GET` would leak the user's entire config to any other tab on the machine. This hook is registered **only inside the `/api` plugin scope** — registering it at the root is 02-RESEARCH.md Pitfall 1 and bricks the SPA bootstrap, because the browser has no token until it has already loaded `index.html`.

    Create `packages/server/src/plugins/cors.ts` exporting `buildCorsOptions(ctx)`, a single factory returning the `@fastify/cors` options object: a function-based `origin` callback that answers `true` only on an exact string equality against `ctx.corsOrigin` (and `false` when `ctx.corsOrigin` is null or the origin is absent), `credentials: false` (the token is a header, not a cookie — this model has no CSRF-via-cookie surface at all), `methods` limited to the verbs the API actually uses, and `allowedHeaders` including `content-type` and `x-gsd-token`. Use exact string comparison only — a pattern-matching origin check is a documented Fastify ReDoS footgun (02-RESEARCH.md Pitfall 6) and is pointless here because the origin is a single known value computed once after bind. Comment the safety reasoning inline, matching `validate.ts`'s style.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any browser tab on the machine → loopback HTTP API | Untrusted. Any page the user visits can issue `fetch()` at `http://127.0.0.1:<port>`. This is the MCP-Inspector-CVE-2025-49596 boundary. |
| Any local process (`curl`, another tool, malware) → loopback HTTP API | Untrusted. Non-browser callers ignore CORS entirely. |
| Attacker-controlled DNS name resolving to 127.0.0.1 → loopback HTTP API | Untrusted. DNS rebinding turns a remote page into a same-origin local caller. |
| Server → response bodies / logs | Outbound. Guard rejections and request logs must not leak the token, the config, or the rejected request values. |
