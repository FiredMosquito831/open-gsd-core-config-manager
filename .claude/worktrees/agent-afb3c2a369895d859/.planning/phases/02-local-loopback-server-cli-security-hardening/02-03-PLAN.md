<objective>
Establish the frozen `dist/client/**` output contract with a minimal, dependency-free placeholder page that demonstrates the D-05 token flow, plus the build step that produces it.

Purpose: DIST-03 requires "a public npm package with the built UI bundled inside it." Phase 3 builds the real schema-driven UI; 02-CONTEXT.md explicitly permits "a placeholder/minimal served page" for Phase 2 verification. What Phase 2 must actually deliver is the *pipeline and the contract*: a stable `dist/client/index.html` that `@fastify/static` (Plan 04) serves, that the tarball (Plan 07) ships, and that Phase 3 later regenerates with Vite without touching anything downstream.

Deliberate scope decision (Claude's Discretion per 02-CONTEXT.md): Phase 2 does **not** install Vite or React. Installing the Phase 3 frontend stack solely to emit a placeholder would add five dependencies that Phase 3 will immediately reconfigure, and would prove nothing that a static page does not. Instead the client build is a copy step today and becomes `vite build --outDir dist/client` in Phase 3 — the output contract is identical, so the server and the packaging pipeline never change.

Output: `web/index.html`, `scripts/build-client.mjs`, and the `build:client` npm script.
</objective>

  <files>web/index.html</files>
  <action>
    Create `web/index.html`: a single self-contained HTML file, no build tooling, no framework, no external assets, no CDN links (it must work offline inside an `npx` install).

    It renders a plain heading identifying the tool, a short line stating that the real config UI arrives in Phase 3, and a live status area. On load, its inline script does exactly what the Phase 3 SPA will do, because this IS the frozen bootstrap contract (D-05):

    1. Read the token once from `new URLSearchParams(location.search).get('t')`.
    2. Immediately remove the token from the address bar with `history.replaceState({}, '', location.pathname)` so it does not persist into browser history, bookmarks, or a `Referer` header. Do not write it to `localStorage` or `sessionStorage` — it lives only in a module-scoped variable for the page's lifetime.
    3. `fetch('/api/health', { headers: { 'x-gsd-token': token } })` — the token travels as a **header**, never as a query parameter on an API call. This is the whole point of D-05: query strings land in server request logs, headers generally do not.
    4. Render the outcome into the status area: on a 200 with `{ ok: true }`, show a "connected" state including the reported version; on a 403, show that the launch token was missing or invalid and instruct the user to re-open the URL the CLI printed; on a network error, show that the local helper is not reachable.
    5. If no `t` query parameter was present at all, skip the fetch and show the "open the URL the CLI printed" message.

    Keep the styling to a handful of inline CSS rules — legible, centered, dark-friendly. Do not introduce a design system, a component library, or Tailwind; 02-UI-SPEC.md scopes this phase's design contract to CLI output only and hands the web UI's visual language to Phase 3.

    The page must never display or log the token value itself.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Launch URL (`?t=<token>`) → browser | The token crosses into browser-controlled storage surfaces: address bar, history, bookmarks, `Referer` headers on any outbound link. |
| Browser page → local API | Every API call from the page must carry the token; the page is the only legitimate holder of it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Information Disclosure | `web/index.html` — launch token persisting in browser history, bookmarks, or leaking via `Referer` to any external resource | medium | mitigate | The page reads `?t=` once and immediately calls `history.replaceState` to drop it from the address bar and history; the token is never written to `localStorage`/`sessionStorage`; the page loads zero external resources, so no `Referer` carrying the original URL is ever sent off-machine. Verified by Task 1's acceptance greps (no storage APIs, no external `src`/`href`, `history.replaceState` present). |
| T-02-04b | Information Disclosure | Token appearing in Fastify request logs because an API call passed it as a query parameter | medium | mitigate | D-05: API calls send `x-gsd-token` as a header. Task 1 asserts no `?t=` is appended to any `fetch` URL. The one-time `?t=` on the initial page load is an accepted, documented single exposure to the local log stream only (02-RESEARCH.md Security Domain). |
| T-02-16 | Tampering | Placeholder page loading remote script/style, creating a supply-chain and exfiltration path from inside an `npx`-launched local tool | medium | mitigate | The page is fully self-contained: no CDN links, no external `src`/`href`, no framework. Asserted programmatically in Task 1's acceptance criteria. |
| T-02-17 | Denial of Service | Stale or missing `dist/client` shipping in the tarball, producing a blank page for every `npx` user | medium | mitigate | The client build is a deterministic, idempotent, scoped-clean step (Task 2), and Plan 07 wires it into `prepublishOnly` and asserts `dist/client/index.html` is present in `npm pack --dry-run --json` output (02-RESEARCH.md Pitfall 5). |
</threat_model>
