<bundled_schema_landmine>
**A packaging landmine 02-RESEARCH.md did not catch. Read before writing `schema.ts`.**

`packages/config-io/src/load.ts` resolves its default schema path from `import.meta.url` (`packages/config-io/src → ../../schema-data/bundled-schema.json`). That works today under `tsx`. It will **break in the published package**: Plan 07 bundles everything into a single `dist/cli.js`, so `import.meta.url` becomes `<pkg>/dist/cli.js` and the relative walk resolves to a path that does not exist in the tarball. The tool would then fail at first load for every `npx` user, and no test that runs from source would ever catch it.

Fix, implemented in this plan: the server never relies on `load()`'s default schema resolution. `packages/server/src/schema.ts` imports the bundled schema as a **JSON module** (`import bundledSchema from '../../schema-data/bundled-schema.json' with { type: 'json' }`), which esbuild/tsup inlines directly into the bundle — no runtime file resolution at all. `tsconfig.json` already has `resolveJsonModule: true`. Every route then passes that schema explicitly into `load(path, { schema })` and into `createValidator(buildAjvSchema(schema))`.

Do NOT "fix" this by editing `packages/config-io/src/load.ts` — it is frozen, its behavior is correct for its own callers, and `LoadOptions.schema` already exists as the intended injection seam.
</bundled_schema_landmine>

    Create `packages/server/src/api-types.ts` defining the frozen response envelope. Every API response is one of exactly two shapes: `ApiOk<T> = { ok: true } & T` or `ApiErr = { ok: false; errors: Array<{ message: string; [k: string]: unknown }> }`.     Create `packages/server/src/registry.ts` exporting `createRegistry()` returning a `ConfigRegistry` with `track(rawPath: string): TrackedConfig`, `list(): TrackedConfig[]`, and `resolve(id: string): TrackedConfig | undefined`. Back it with an in-memory `Map<string, TrackedConfig>`; persistence across sessions is DISC-02, a Phase 3 requirement — do not build it here, but do keep `createRegistry()` a factory (no module-level singleton) so Phase 3 can hand it a persisted seed without restructuring anything.

    `track()` is the **only** place in the entire API where a client-supplied filesystem path is accepted, which makes it the entire path-traversal boundary. It must: reject a non-absolute path; `path.resolve()` the input and use the resolved form thereafter; reject anything whose basename does not end in `.json`; reject a path that exists but is not a regular file. Throw a typed `RegistryError` carrying a static message on each rejection — never echo the offending path back in the message (a rejected path is attacker-controlled input; reflecting it is a disclosure oracle). Compute `id` as the first 32 hex chars of `sha256(resolvedPath)` — the same hashing scheme the snapshot store uses for its directory key, so an id and a snapshot dir are trivially correlatable in Phase 5. Tracking the same path twice returns the same id and does not duplicate the entry.

    Every other route resolves `:id` through `resolve(id)` and gets a path the server itself minted. A client can never name a file the server has not already validated and accepted.

    Create `packages/server/src/schema.ts` exporting `getBundledSchema(): Record<string, SchemaEntry>` and `getValidator(): (data: unknown) => ValidationResult`. Import the schema as a JSON module (see `<bundled_schema_landmine>`), and build the validator once via `createValidator(buildAjvSchema(getBundledSchema()))`, memoized at module scope — Ajv compilation is expensive and the schema never changes at runtime.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client request body / route params → filesystem path resolution | The highest-risk boundary in the phase: the API can read and write files. A path crossing this boundary unvalidated is arbitrary file read/write. |
| Client request body → config file content | Untrusted JSON becomes the user's config. Must pass Phase 1's Ajv gate before any byte is written. |
| Save path → snapshot store | Every save copies the prior config into app-data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Tampering | `routes/configs.ts` / `registry.ts` — path traversal or arbitrary file read/write via a client-supplied config path | high | mitigate | Read and write routes accept **only an opaque id**, resolved against the server-held registry; they never see a path. `track()` is the single entry point that accepts a path and it rejects non-absolute paths, non-`.json` targets, and non-regular files, `path.resolve()`s before use, and never echoes the rejected path back. Verified: api-routes.test.ts "rejects a relative path on track", "rejects a traversal path on track", "rejects an unknown config id", "never accepts a filesystem path on the save route". |
| T-02-23 | Tampering | `PUT /configs/:id` — an invalid or hostile config body corrupting the user's config | high | mitigate | The write is delegated to `saveWithSnapshot` → Phase 1's frozen `saveConfig`, whose validate-blocks-write gate (SAVE-01) throws before any byte is written; the route maps that to 422 with field errors. `routes/configs.ts` performs no filesystem write of its own (asserted by a comment-filtered grep). Verified: "returns 422 with field errors when the saved config fails schema validation" asserts the file is byte-unchanged. |
| T-02-24 | Elevation of Privilege | Prototype pollution via a `__proto__`/`constructor` key in the `PUT` body reaching the config object | high | mitigate | Phase 1's `safeSet` is the only patch primitive and Ajv validates the body before the write; the route passes the body through to `saveConfig` without spreading or deep-merging it onto any existing object. |

| T-02-25 | Information Disclosure | `RegistryError` messages reflecting the rejected path back to the caller (a filesystem-probing oracle: existence, type, and traversal reachability) | medium | mitigate | `RegistryError` carries a fixed static message per rejection reason; the submitted path is never interpolated.
